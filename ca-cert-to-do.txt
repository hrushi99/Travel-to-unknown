3. Category 1 — Internal Root CA (Legacy + CMS)
Cluster-admin, one-time/rare operation — not part of per-service GitOps flow.
apiVersion: v1
kind: ConfigMap
metadata: {name: sbi-internal-root-ca, namespace: openshift-config}
data:
ca-bundle.crt: |-----BEGIN CERTIFICATE----
... (Legacy Root CA)-----END CERTIFICATE----------BEGIN CERTIFICATE----
... (New CMS Root CA)-----END CERTIFICATE----
oc patch proxy/cluster --type=merge -p '{"spec":{"trustedCA":{"name":"sbi-internal-root-ca"}}}'
Both CAs concatenated — required during the legacy→CMS coexistence window. Confirm with your PKI team
before ever removing the legacy CA; do it only once every leaf cert it issued has migrated to CMS-issued
replacements.
Impact: triggers a cluster-wide rolling node reboot (Machine Config Operator) — schedule as a planned
maintenance window, dev → preprod → prod, not routine change.
App wiring:
spring.ssl.bundle.pem.internal-root.truststore.certificate=file:/etc/pki/ca
trust/extracted/pem/tls-ca-bundle.pem
spring.http.client.ssl.bundle=internal-root
spring.http.reactiveclient.ssl.bundle=internal-root
Covers SMS, S3/NetApp, email, JFrog, GitLab, and any other internally-signed endpoint automatically once a leaf
cert chains to either root — no per-service action needed beyond the master chart default (

If the current WAF-CSR → PKCS12 → JKS process is driven by legacy code with no injection point:
initContainers:- name: npci-keystore-build
image: epay-jf
command: ["/bin/sh", "-c"]
args:- openssl pkcs12 -export -in /opt/certs/npci/tls.crt -inkey /opt/certs/npci/tls.key-out /keystore/npci-keystore.p12 -password pass:$(KEYSTORE_PASSWORD)
volumeMounts:- {name: npci-client-cert, mountPath: /opt/certs/npci}- {name: npci-keystore-vol, mountPath: /keystore}

Djavax.net.ssl.keyStoreType=PKCS12 -Djavax.net.ssl.keyStorePassword=$(KEYSTORE_PASSWORD)"
Even in the fallback, the source private key still comes from an OpenShift Secret, not a Dockerfile — rotation
still avoids an image rebuild; only the runtime conversion step (not the storage/build dependency) is retained.
Do not add the private key to a truststore. Category 3's Secret contains

7
. Secret Provisioning Without Sealed Secrets — Operational Process
Since Categories 3–4 hold private key material and Sealed Secrets is explicitly out of scope for now, plain 
Secret
creation must happen outside the Git-tracked deployment-repo flow — Secret YAML is only base64, never
commit it, encrypted or not.
7
.1 Provisioning procedure (interim, until Vault)
1. Cert/key received from NPCI/CA out-of-band (secure channel per existing process).
2. Platform team (or designated Release Manager, per your no-Owner-role RBAC model) runs 
/ 
oc apply -f
directly against each cluster — not via ArgoCD sync.
oc create secret
3. Log the change in your existing change-management/ticketing process (cert alias, cluster, date, requestor) —
this becomes your audit trail in place of Git history, required for PCI-DSS Req 10.5.1 evidence.
4. Repeat independently per cluster (dev, preprod-dc, preprod-dr, prod-dc, prod-dr) — no automatic propagation
between clusters for Secrets, unlike the ConfigMap-based categories.
7
.2 Keep ArgoCD from fighting the Secret
Since the Secret is created out-of-band, exclude it from ArgoCD's managed-resource diffing to avoid drift alerts or
accidental pruning:
# Application manifest, or via annotation on the Secret itself
metadata:
annotations:
argocd.argoproj.io/compare-options: IgnoreExtraneous
Or scope the ArgoCD 
Application 
's resource inclusion to exclude 
kind: Secret
 for the relevant path entirely, if
your Application definitions support a path-level exclusion — confirm against your current ArgoCD app-of-apps
structure before rollout.
7
.3 Rotation
Same 
oc create secret ... --dry-run=client -o yaml | oc apply -f 
 pattern, re-run per cluster →
Reloader (already watching the Secret name via the master chart's 
secret.reloader.stakater.com/reload
annotation) triggers pod restart automatically. No image rebuild, no Git commit, no ArgoCD sync — the one
deliberate gap versus Categories 1–2, accepted as the interim state.

Same CronJob pattern as before, now also checking the NPCI client cert:
#!/bin/sh
set -e
WARN_DAYS=30
NOW=$(date +%s)
check_one() {
cert_file=$1; label_type=$2; cert_id=$3
cn=$(openssl x509 -in "$cert_file" -noout -subject 2>/dev/null | sed -n 's/.*CN *= *\
([^,\/]*\).*/\1/p')
exp=$(openssl x509 -in "$cert_file" -noout -enddate | cut -d= -f2)
exp_epoch=$(date -d "$exp" +%s)
days_left=$(( (exp_epoch - NOW) / 86400 ))
echo "cert_expiry_days{service=\"payment
svc\",type=\"$label_type\",cert_id=\"$cert_id\",cn=\"$cn\"} $days_left" >> /metrics/expiry.prom
[ "$days_left" -lt "$WARN_DAYS" ] && echo "ALERT: [$label_type:$cert_id] $cn expires in 
$days_left days"
}
# Category 2 — split bundle, check each
awk '/^# cert-id:/{id=$0; sub("# cert-id: ","",id)} /-----BEGIN CERTIFICATE-----/{n++; 
ids[n]=id} {print > ("/tmp/cert-" n ".pem")}' /opt/certs/trust/trust-bundle.pem
i=1
for f in /tmp/cert-*.pem; do [ -s "$f" ] || continue; check_one "$f" "trust" "${ids[$i]:
unknown}"; i=$((i+1)); done
# Category 3 — NPCI client cert
[ -f /opt/certs/npci/tls.crt ] && check_one /opt/certs/npci/tls.crt "npci-client" "npci-client
cert"
curl --data-binary @/metrics/expiry.prom 
"http://pushgateway.monitoring.svc:9091/metrics/job/cert-expiry/instance/payment-svc"
